## 1. Security findings

### H1 — `file:` whitelisted for remote HLS → local-file read via malicious playlist

`src/downloader.js:1449`:

```js
args.push('-protocol_whitelist', 'file,http,https,tcp,tls,crypto,data');
args.push('-allowed_extensions', 'ALL');            // :1456
if (ffmpegSupportsExtensionPicky(ffmpegPath)) args.push('-extension_picky', '0');
```

This is applied to **every** HLS input, including `https://` playlists fetched from the
site being downloaded. ffmpeg's HLS demuxer applies the same whitelist to every nested
open (segments, `#EXT-X-MAP` init sections, `#EXT-X-KEY` URIs). Its default for a remote
playlist deliberately excludes `file` — that default *is* the fix for
CVE-2016-1897/1898 and CVE-2017-9993 (HLS playlists referencing local files). Adding
`file` removes that defence, and `-allowed_extensions ALL` + `-extension_picky 0` remove
the second layer (segment-name filtering). A site — or anyone who can MITM the yt-dlp
fallback, see M2 — can serve a playlist whose segments point at
`file:///config/database/global/users.json` or a user's `cookies.txt`; ffmpeg reads them
into the output the user then downloads. Exploit payload details vary by ffmpeg version
(the bytes must survive the segment demuxer), so treat this as "defence removed, exposure
real" rather than a proven byte-exact exfil.

Why `file` was added: the downloader sometimes writes a **local** temp variant playlist
(`.vdl_variant_<ts>.m3u8`, `downloader.js:1328`) and hands its path to `-i`, and ffmpeg
needs `file` to open that input.

**Fix (small):**
1. Only include `file` when `hlsUrl` is a local path; for `http(s)` inputs use
   `http,https,tcp,tls,crypto,data`.
2. Better: drop `file` entirely by feeding the temp variant as a `data:` URI
   (`-i data:application/vnd.apple.mpegurl;base64,<playlist>` — `data` is already
   whitelisted), so no local file is ever an ffmpeg input. This also removes the temp
   file from the user's download folder (it is written to the Samba share today).
3. Keep `-allowed_extensions ALL` (HentaiHaven needs it) — it is only dangerous in
   combination with `file`.

### H2 — `custom_name_prefix`: path traversal + un-substituted output template **[verified]**

Flow: `POST /add {custom_name_prefix}` (`main.py:664`, no sanitisation) →
`args.extend(['-o', f'{prefix}.%(title)s.%(ext)s'])` (`videodl_engine.py:170`) →
`filename = options.output` verbatim (`cli.js:671`, `:1621`) →
`uniqueFilepath(path.join(directory, filename))`.

Reproduced on 2026-09-13 with the CLI from source:

```
-d …/otest/inner  -o '../ESCAPED.%(title)s.%(ext)s'
→ Saving to: …/otest/ESCAPED.%(title)s.%(ext)s        (parent of -d; literal template)
```

Consequences:
- **Traversal:** any authenticated user can write video bytes to an arbitrary path
  the container process can reach (uid 0 → anywhere writable), including other users'
  download homes, bypassing the per-user confinement that `_resolve_download_file`
  enforces on the *read* side. `uniqueFilepath` + the literal suffix mean existing files
  are not overwritten, so this is a write-anywhere primitive, not an overwrite.
- **Functional bug:** the Angular UI exposes the prefix field (`ui/src/app/app.ts:56`),
  and every download using it is saved as `prefix.%(title)s.%(ext)s` — wrong name,
  no usable extension, and the engine records that name in history.

**Fix:**
- Server side (`main.py`): sanitise the prefix the same way `sanitizeFilename` does in
  the CLI — strip `/`, `\`, NUL, control chars, leading dots, `..`; cap length.
- CLI (`cli.js`): resolve `path.join(directory, output)` and refuse if it is not inside
  `path.resolve(directory)`; and either implement `%(title)s` / `%(ext)s` substitution
  (a five-line `replace`) or have the engine send only the prefix and let the CLI build
  the name (`prefix.<sanitized title>.<ext>`). The second is simpler and keeps one
  naming code path.

### H3 — Remote JavaScript executed in-process

`youtube.js:205` builds the solver with `new Function('meriyah','astring', solverCode)`
(the vendored `yt.solver.core.js`, identical to `yt-dlp/ejs` 0.8.0 — verified by
EOL-normalised sha256). The solver then executes YouTube's **player challenge code**
via `Function('_result', code)(resultObj)` (`vendor/yt.solver.core.js:319`). That code
comes from `https://www.youtube.com/s/player/…/base.js` fetched at runtime and runs with
the CLI's full privileges: `fs`, `child_process`, network, `/config`.

yt-dlp ships this exact solver but runs it in an external runtime, preferring **deno
with no permissions** — the code cannot touch the filesystem or network. We have no
equivalent boundary. Today the trust anchor is TLS to youtube.com (the YouTube path uses
`got` with certificate verification, unlike the yt-dlp fallback), so the practical risk
is a compromised/misissued cert or a compromised player-JS CDN — low probability, total
impact.

**Fix options, in order of strength:**
1. **Child process with the Node permission model.** The SEA is a Node ≥ 24 binary;
   spawn *itself* as `videodl-ffmpeg --solve-challenge` with
   `--permission` (Node's permission model: no fs, no child_process, no worker unless
   `--allow-*` given) and pass the player JS + requests over stdin, results over stdout,
   with a timeout. This mirrors yt-dlp's deno sandbox and needs no new dependency.
   Node ≥ 20 supports `--permission` (`--experimental-permission` on 20/22).
2. Interim: run the solver in `node:vm` (`runInNewContext` with a bare context and
   `timeout`). Cheap, but Node documents `vm` as *not* a security boundary — it stops
   accidents, not a determined payload.

### M1 — SSRF from the web UI

`POST /add` accepts any URL; native extractors and the yt-dlp fallback (`canHandle`
= any `http(s)://`) fetch it; `got` follows redirects (only reddit/imgur/pornzog/tiktok
set `followRedirect:false`, for other reasons); the body lands in the user's download
folder and is served back by `/download/...`. There is no check anywhere for loopback,
RFC1918, link-local, or CGNAT ranges. Practical targets on this LAN: Ollama on
`11.1.0.2:11434` (`/api/tags`, model pulls), the MikroTik REST API, other pods, and the
container's own API from `127.0.0.1` (session-cookie-gated, so limited). The HTML guard
(`_looks_like_html`) deletes HTML bodies only; JSON/text survive.

**Fix:** in `add` (and ideally in the CLI too so the CLI is safe standalone): resolve the
hostname, reject if any A/AAAA is loopback / private / link-local / CGNAT / multicast /
the `169.254.169.254` metadata address, unless the URL host is on an admin allowlist
(the IndaPlay `cms.` host is public, so nothing legitimate breaks). Re-check on every
redirect (`got` `hooks.beforeRedirect`). Block non-`http(s)` schemes explicitly.

### M2 — `--no-check-certificates` on the yt-dlp fallback path

`ytdlp.js:82` and `:143` disable TLS verification for **all** yt-dlp extraction — the
1000+-site path — and yt-dlp is also handed the user's cookie file (`--cookies`). Any
on-path attacker can serve a fake site, harvest cookies, and (via H1) a malicious HLS
playlist. The CLI already has `--no-ssl-verify` / `options.sslVerify` plumbing
(`cli.js:744` etc.); the fallback should honour it instead of hard-coding the bypass.

### M3 — No throttling on the password step of `/api/login`

`user_manager.authenticate()` (`:301`) has no failed-attempt tracking; penalties exist
only for 2FA (`:623`) and recovery (`:1542`). A LAN attacker can brute-force passwords
at aiohttp speed. Also: sessions live 7 days (`SESSION_TTL`, `:103`) with no rotation;
the login response distinguishes "disabled user" from "bad password" (user
enumeration). **Fix:** per-username *and* per-IP exponential backoff on password
failure (reuse the recovery-penalty code), uniform error text.

### M4 — Supply chain / reproducibility (blocks safe automated updates)

| Input | Today | Risk |
|-------|-------|------|
| npm dependencies (`got`, `cheerio`, `puppeteer-*`, `cycletls` incl. a **Go binary**) | `package-lock.json` is in `.gitignore`; `compile.sh:168-170` runs `npm install` and *skips it if `node_modules` exists* | Every build resolves fresh ranges → non-reproducible; a malicious minor release is picked up silently; the share's stale `node_modules` may differ from a clean build |
| Node.js for the SEA | `compile.sh:53` uses the **build host's** `node --version`; tarball fetched with no checksum (`:101-110`) | Binary = f(host state); no integrity check |
| Node.js in the container builder | `Dockerfile:23-25` scrapes `latest-v22.x/` and downloads with no `SHASUMS256.txt` check | Same |
| ffmpeg embedded in the SEA | `build.mjs:418` → BtbN `releases/latest` (`master-latest`), no checksum | Moving target inside the shipped binary |
| yt-dlp in the container | `Dockerfile:72` `pip install … yt-dlp` — no version, no `--hash` | Unpinned; PyPI compromise → RCE in the container |
| `yt.solver.core.js` | vendored, no recorded upstream tag/hash | Cannot tell drift; currently == ejs 0.8.0 |

None of these is a vulnerability today; together they make "rebuild to update yt-dlp"
change four other things at once. Fixes are in §4 (they are the pipeline's
prerequisites).

### M5 — Session cookie without `Secure`

`main.py:1050`: `httponly=True, samesite='Strict'` but no `secure=True`. Fine while
the UI is plain HTTP on the LAN; **must** be set (and `request.secure`/`X-Forwarded-*`
trusted only from the proxy) the day it is fronted by TLS or a Cloudflare tunnel.

### Low

- **L1** Container runs as uid 0 inside (`-e UID=0 -e GID=0` in
  `/etc/scripts/podman-videodl-updater-inside-pod`; the entrypoint even warns). Rootless
  mapping bounds it to host user 10019, but H1/H2 impact scales with it. Run as a
  non-zero UID and `chown` the volumes once.
- **L2** `-H` header values are not stripped of CR/LF (`cli.js:1194`) and are joined with
  `\r\n` into ffmpeg `-headers` (`downloader.js:1430-1437`) → header injection. Only the
  CLI user can trigger it (the UI never sends `-H`), so self-inflicted; still sanitise.
- **L3** `canHandle()` matches the domain **anywhere in the string** in ~20 extractors
  (`/pornhub\.com/i`, `/(?:youtube\.com|youtu\.be)/i`, `indavideo`, my `indaplay` /
  `indaevents`, …). `https://example.com/?u=youtube.com` routes to YouTube. Add a
  `hostMatches(url, domains)` helper in `base.js` that parses `new URL(url).hostname`
  and matches exact/suffix; migrate extractors as they are touched.
- **L4** `videodl_engine.py:780-784` builds a `sqlite3 … | sqlite3 …` command string with
  `shell=True` from `self.path`. The path is internal, so not injectable today, but it
  is a needless shell; use argv + `subprocess` pipes.
- **L5** `.dockerignore` lacks `*.bak` and `__pycache__`; `app/videodl_engine.py.bak`
  (46 KB of older engine code) and bytecode are baked into the image.
- **L6** The direct (non-HLS) download path has no `Content-Type` rejection; the
  container guards after the fact by deleting HTML (`_looks_like_html`). Root-cause fix
  belongs in `downloader.js` (`LESSONS-LEARNED.md #16` already says so).
- **L7** `ytdlp.js:_parseSingleVideo`: `!f.url.includes('videoplayback') === false`
  parses as `(!includes) === false`, i.e. *keep only* URLs containing `videoplayback`.
  For non-YouTube sites that yields an empty list and the fallback branch returns
  everything — it works by accident and drops YouTube HLS manifests. Simplify to
  `f.ext !== 'mhtml' && f.url`.

### What is in good shape

- yt-dlp is invoked with `execFile` + argv + `--` (`ytdlp.js:87`) — no shell, no option
  injection from URLs. ffmpeg likewise via `spawn` with argv.
- Passwords: PBKDF2-SHA256, 260 000 iterations, per-user salt, legacy SHA256 hashes
  migrated on next login (`user_manager.py:60-80,311`). (OWASP's 2023 figure is 600 000;
  bumping is cheap.) Session/2FA/reset tokens from `secrets`.
- Download/audio file routes and `folder` are confined with `realpath` +
  inside-base checks (`main.py:384-412`, `videodl_engine.py:997-1005`) — the v2.0.116
  fix holds.
- Admin routes call `_require_admin` / `_require_admin_or_useradmin`.
- Only `:8081` listens inside the container (checked live via `/proc/net/tcp`).
- `cookies/` and `logins/` hold only `.example` files and real ones are git-ignored.
- Live yt-dlp is `2026.08.19` — identical to upstream's latest as of today, and the
  vendored solver is byte-identical (modulo CRLF) to `yt-dlp/ejs` 0.8.0.

Noticed outside the repos, not part of this review: `Z:\Temp\git\scripts\MobaXterm
Stored Passwords.txt` is a plaintext credential export on the share. `scripts/` is not a
git repo, so it is not pushed anywhere — but it should not sit on a share.

## 2. Code-quality improvements (non-security)

**Cross-cutting**
- The **CRLF churn trap** (every session has to hand-normalise EOLs; documented in
  `UPDATE-FROM-YTDLP.md` step 3 and memory) is solvable once: add
  `* text=auto eol=lf` to `.gitattributes`, run `git add --renormalize .`, one
  normalisation commit. After that Windows/Samba edits stop showing phantom diffs.
- `_decodeHtmlEntities` is copy-pasted into ~10 extractors with slightly different
  entity sets → one implementation in `base.js`.
- `cli.js` (105 KB) and `downloader.js` (72 KB) are monoliths; the `download` and
  `download-json` commands duplicate the filename/format-selection logic (`:647-700`
  vs `:1388-1450`, where H2 lives twice). Extract a shared `resolveOutputPath()`.
- `compile.sh` skips `npm install` when `node_modules/` exists → builds from whatever
  the share holds. Use `npm ci` unconditionally (fast with a lockfile).

**IndaPlay / IndaEvents (my own, from 2026-09-06)**
- `canHandle` has the L3 substring problem (`/(^|[/.])(?:cms\.)?indaplay\.hu\//`
  matches `evil.com/indaplay.hu/`). Switch to hostname matching.
- `extract()` falls back to `${CMS}/static/streaming-playlists/hls/${uuid}/master.m3u8`
  when both API and page fail — that path shape does not exist on PeerTube
  (`<playlistUuid>-master.m3u8`), so it can only 404. Remove the guess; keep the
  page-derived `playlistUrl`.
- `_resolveSlug` re-fetches the original URL as its own first candidate when the caller
  already gave `/hu/video/<ch>/<slug>`. De-duplicate candidates.
- `_pageVideos` finds the video name with a look-ahead trick
  (`"name":"…"(?=[^"]*$)`); a global match taking the last hit is clearer.
- `encodeURIComponent` the channel/slug segments when building portal URLs.

**yt-dlp fallback**
- L7 above; and `findYtdlp()` caches "not found" for the process lifetime — fine for the
  CLI, but the container process is long-lived: a yt-dlp install after start is never
  seen (not an issue in the image, worth a comment).

## 4. Automated, harmless updates from yt-dlp — design

### 4.1 What "from yt-dlp" actually means here

Three separate things in this project derive from yt-dlp, and they need three different
update mechanisms:

| Component | Where | Update = | Risk to *our* binary |
|-----------|-------|----------|----------------------|
| **A. yt-dlp itself** (fallback for 1000+ sites) | Python package in the container venv | bump a pin, rebuild the image | **None** — it is a separate executable; the SEA is untouched |
| **B. Challenge solver** `yt.solver.core.js` | `src/vendor/`, compiled into the SEA | replace one file from `yt-dlp/ejs` release, recompile | Low — data-like; breaks only YouTube if wrong |
| **C. InnerTube client table** | `src/extractors/youtube.js` | reconcile with `_base.py`; human judgement (ANDROID_VR ≤ 1.65 pin) | Medium — logic; needs a human, but the *diff* can be automated |

Porting yt-dlp's Python extractors to our JS ones automatically is not realistic and is
not what we need — the fallback (A) already covers those sites.

`yt-dlp -U` inside the running container is **not** an option: pip-installed yt-dlp
doesn't support it, it would be unverified, non-reproducible, and lost on the next
`podman rmi` (the updater script deletes the image every deploy).

### 4.2 Principle: one pin moves per run, everything else is frozen, a test gate decides

"Could cause no harm to our binary" is only achievable if a rebuild reproduces the
previous binary except for the one deliberate change. Today it cannot (M4). So the
pipeline has **prerequisites** (one-off, in the repos):

1. **Commit `package-lock.json`** (remove from `.gitignore`); `compile.sh` uses `npm ci`.
2. **Pin Node** for the SEA and the container builder to an exact version in one place
   (`NODE_VERSION=24.x.y`); download `SHASUMS256.txt` (+ `.sig`, Node release keys) and
   verify the tarball before extracting. Replace the `latest-v22.x` index scrape.
3. **Pin BtbN ffmpeg** to a dated release tag (`autobuild-YYYY-MM-DD-HH-MM`) and record
   the artefact sha256 in `build.mjs`; fail the build on mismatch.
4. **Pin yt-dlp** in the container as `requirements.txt` with
   `yt-dlp==2026.8.19 --hash=sha256:…` and `pip install --require-hashes -r …`
   (same for aiohttp/python-socketio/pyotp/qrcode — `pip-compile --generate-hashes`).
5. **Record the solver provenance**: `src/vendor/ejs.lock.json` → `{ "tag": "0.8.0",
   "sha256": "…" }`, checked by `compile.sh`.

With those in place, "update yt-dlp" is a one-line diff in `requirements.txt`, and a
rebuild for it changes nothing else.

### 4.2b Propagation rule: every upstream change ends in a **container** release

The container is the engine's only production home: it embeds the CLI binary at build
time (`build.sh` → `gh release download` → `/videodl-cli/videodl-ffmpeg`) and it is the
only place the yt-dlp Python package exists. So an upstream change is never "done" when
`videodl-script` is updated — it is done when the **container** that embeds the result
is built, released, deployed and verified. The two repos share one version sequence and
must move in lock-step, CLI first:

| Upstream change | `videodl-script` | `videodl-container` | Order |
|-----------------|------------------|---------------------|-------|
| **A** yt-dlp package | — (nothing to change) | `requirements.txt` pin + hash → `build.sh` | container only |
| **B** solver `yt.solver.core.js` | replace file, `ejs.lock.json`, commit → `compile.sh` (new CLI release) | `build.sh` embeds the new CLI tag → release → deploy | CLI **then** container |
| **C** InnerTube client table | edit `youtube.js`, commit → `compile.sh` | same as B | CLI **then** container |
| B or C **and** A together | as above | one container build carries both (new CLI tag + new pin) | CLI, then one container build |

Consequences for the job:
- `promote` **always** runs the container `build.sh` + deploy, even for a B/C-only
  change where `videodl-script` was the thing edited — otherwise production keeps the
  old engine while GitHub shows a new CLI release (the exact drift that bit before:
  script 2.0.132 shipped, container CHANGELOG never recorded 2.0.133).
- The container build must embed the CLI tag the run just published (it already logs
  `Mode: embedded (videodl-cli tag: vX.Y.Z)`); the job asserts that tag equals the one
  `compile.sh` produced, not `latest`, so a parallel release cannot sneak in between.
- The deployed-verify step checks **both engines inside the running container**:
  `/videodl-cli/videodl-ffmpeg --version` (the CLI tag) and `/opt/venv/bin/yt-dlp
  --version` (the pin) — and runs the smoke suite through the deployed container, not
  the build host.
- Both CHANGELOGs get an entry per run; the container entry names the embedded CLI
  tag and the yt-dlp version, so "which engine is live?" is answerable from git.
- Expose the yt-dlp version alongside the CLI version in the container's version/status
  endpoint (`main.py` already reports the CLI version via `--version`), so the web UI
  footer shows both and a stale engine is visible without `podman exec`.

### 4.3 The job: `update-from-upstream.sh` (evolves `update-from-ytdlp.sh`)

Run as root on 11.1.0.2 (it already has `gh`, `podman`, the repos), weekly via a
systemd timer **and** on demand. Stages, each idempotent:

```
check     → what moved upstream? (yt-dlp tag, ejs tag, INNERTUBE_CLIENTS diff)
verify    → fetch + verify: yt-dlp SHA2-256SUMS + .sig against public.key, PyPI hash;
            ejs asset → compute sha256 (no upstream sums exist)
stage     → write the ONE pin change to a git branch `upstream/<date>`; build the CLI
            (if B changed) and a candidate image tagged ghcr…/videodl:candidate
            — never :latest
test      → run tests/smoke-urls.json against a throwaway container from :candidate
            (see 4.4); collect a report
promote   → only if test is green: merge, compile.sh/build.sh as today (releases,
            :latest), deploy with the existing rootless updater, verify the DEPLOYED
            binary with the same suite
report    → write UPDATE-REPORT-<date>.md (what moved, hashes, test table, decision);
            on red: leave the branch + :candidate for a human, deploy nothing
```

Decision rules baked in:
- **A (yt-dlp)**: fully automatic — stage/test/promote. A red suite leaves the old pin.
- **B (solver)**: automatic when the YouTube smoke cases pass; otherwise report.
- **C (client table)**: `check` produces a machine diff (parse `INNERTUBE_CLIENTS` with a
  small Python `ast` walker → JSON; compare with ours) and **always stops for a human**
  when it differs — the ANDROID_VR ≤ 1.65 pin and the client ordering are judgement
  calls (`LESSONS-LEARNED.md #14`). Optional later step: move our table into
  `clients.json` + an `overrides.json` so the reconcile is a data edit, not a code edit.
- Never more than one component per run. If A and B both moved, run A first; B next run.

### 4.4 The gate: `tests/smoke-urls.json`

A fixed list of stable public URLs with expectations, exercised through the **public
entry point** (`videodl-ffmpeg extract <url>` / `list-formats`), so it measures the
binary users get, not a copy:

```json
[
  { "url": "https://cms.indaplay.hu/videos/watch/6b595ab7-de9c-443f-ac76-2b52a19c5145",
    "extractor": "IndaPlay", "minFormats": 3, "probe": true },
  { "url": "https://www.youtube.com/watch?v=<stable CC video>", "extractor": "YouTube",
    "minFormats": 4, "probe": true, "requires": "solver" },
  { "url": "https://vimeo.com/<staff pick>", "extractor": "Vimeo", "minFormats": 1 },
  { "url": "https://www.dailymotion.com/video/<id>", "extractor": "Dailymotion", "minFormats": 1 },
  { "url": "<a site only yt-dlp handles>", "extractor": "yt-dlp:*", "minFormats": 1, "requires": "ytdlp" }
]
```

Pass criteria per case: routed to the expected extractor, `status ok`, ≥ `minFormats`,
and for `probe: true` a **5-second partial download** succeeds and `ffprobe` sees a
video stream (this is what catches H1-style regressions and the HTML-saved-as-video
bug). The same suite is the regression gate for the fixes in §1.

Rollback is free: every release stays on GitHub and ghcr; the updater script should
accept a tag (`podman pull ghcr.io/hemues/videodl:v2.0.135`).
